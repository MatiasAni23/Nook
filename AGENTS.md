# AGENTS.md — Instrucciones para trabajar en Pinwi

Este archivo orienta a los asistentes de programación que trabajan en este repositorio. Contiene contexto, convenciones y comprobaciones del proyecto; no es código ejecutable ni sustituye la documentación técnica. Mantenerlo actualizado cuando cambien la arquitectura, los comandos o las reglas del negocio.

## Contexto y tecnologías

- Pinwi es una aplicación web para descubrir y gestionar espacios de estudio y trabajo, con perfiles, chat y paneles de administración y delegados. El nombre de la carpeta local es Nook.
- El proyecto proviene de una exportación de Figma y combina funcionalidades conectadas a Supabase con datos y recorridos demo. Verificar la implementación de cada pantalla antes de asumir que una funcionalidad está completa.
- Stack actual: React 18, TypeScript 5 en modo estricto, Vite 6, React Router 7 y Tailwind CSS 4. La interfaz reutiliza componentes shadcn/Radix, Lucide y Recharts. Google Maps usa `@vis.gl/react-google-maps`.
- Backend: Supabase Auth, PostgreSQL con RLS, Storage, Realtime y funciones Edge en Deno. Las invitaciones por correo integran Brevo desde el servidor.
- Correos: `supabase/functions/_shared/emailTemplates.ts` comparte el diseño de Pinwi y el fallback de invitaciones. `npm run emails:generate` genera los HTML de `supabase/templates/`, sus asuntos/preheaders en `manifest.json` y vistas previas ficticias en `docs-local/email/`. Los códigos de registro/recuperación usan `{{ .Token }}` de Supabase Auth; Brevo los entrega por SMTP. Las invitaciones personalizadas usan el ID numérico `BREVO_DELEGATE_TEMPLATE_ID`, no el nombre en Brevo: renombrar la misma plantilla a `delegates_invitation` conserva la integración. `expires_at_label` añade el vencimiento del servidor formateado en `America/Santiago`, conservando `expires_at`. Los siete diseños de avisos opcionales no activan notificaciones ni MFA. Para publicar diseños, usar una configuración aislada que sólo declare las plantillas; no empujar toda la configuración local de Auth/SMTP.
- El logo de correos está en `assets/email/pinwi-logo-v1.png`, exportado de los SVG originales a 552 × 180 y mostrado a 184 × 60. Usa una URL pública estable en Storage desde `emailBrand.logoUrl`, sin enlaces firmados, con texto alternativo. El pie comparte `info@pinwi.cl`, el sitio y los enlaces legales; agregar redes/WhatsApp sólo después de comprobar la configuración pública real. Cambiar el nombre versionado del PNG si cambia el arte, por su caché de un año. Mantener legibles los correos con imágenes bloqueadas y su pie en una columna en móvil.
- Usar `package.json`, `package-lock.json`, la configuración y el código como referencia del estado local. Algunos textos de `README.md` y los informes locales de `docs-local/` describen etapas anteriores o trabajo pendiente.

## Documentación y Expo

- Consultar documentación oficial compatible con las versiones instaladas al introducir una API o resolver dudas. TypeScript es el lenguaje principal; React, Vite y Expo son herramientas del ecosistema, no lenguajes.
- Este repositorio actualmente no declara `expo` ni `react-native`, y usa Vite y componentes del navegador. Los recursos móviles y las exclusiones de Expo en `.gitignore` no cambian ese stack.
- Se conserva la referencia original de Expo SDK 56: https://docs.expo.dev/versions/v56.0.0/. Si una tarea incorpora Expo o trabaja sobre código Expo, leer esa documentación versionada antes de escribir código y comprobar la versión objetivo. No aplicar instrucciones de Expo Router, Metro o componentes nativos al frontend Vite.
- No migrar el proyecto a Expo, actualizar versiones mayores ni cambiar el gestor de paquetes como parte de una tarea que no lo requiera.

## Comandos y configuración local

Usar npm y conservar `package-lock.json`. Existe configuración de pnpm, pero el lockfile y los comandos documentados actuales son de npm. En PowerShell, usar `npm.cmd` si la política de ejecución bloquea `npm.ps1`.

| Comando | Uso |
| --- | --- |
| `npm ci` | Instalar las dependencias del lockfile cuando sea necesario. |
| `npm run dev` o `npm start` | Iniciar el servidor Vite. |
| `npm run typecheck` | Comprobar tipos con `tsc --noEmit`. |
| `npm test` | Ejecutar la suite con el runner de Node. |
| `npm run build` | Compilar la aplicación web en `dist/`. |
| `npm run seo:check` | Verificar HTML, canonicals, robots, sitemap y recursos públicos después de compilar. |
| `git diff --check` | Revisar errores de espacios en los cambios. |

- No hay un script de lint configurado. No afirmar que se ejecutó uno ni instalar herramientas sólo para simular esa comprobación.
- Variables del frontend: `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` o `VITE_SUPABASE_ANON_KEY`, y `VITE_GOOGLE_MAPS_API_KEY`. La clave publishable tiene prioridad sobre la anon.
- `VITE_TURNSTILE_SITE_KEY` prepara el CAPTCHA de Auth; requiere activar Turnstile en Supabase y configurar `TURNSTILE_SECRET_KEY` en las funciones Edge al desplegar. La clave secreta nunca usa `VITE_`. Vite rechaza claves de servidor en variables públicas antes de compilar.
- No hay `.env.example`: crear `.env` sólo con la configuración local autorizada. No generar ejemplos a partir de credenciales reales.
- Sin configuración Supabase, varias rutas y pantallas permiten modo demo. Ese comportamiento no acredita autenticación ni autorización de producción. No convertir errores del backend configurado en éxitos simulados.
- `CheckoutView.tsx` usa datos mock y una alerta; todavía no crea ni cobra una reserva real. No presentar ese recorrido como integración de pagos terminada.
- Las reservas de prueba reales usan `ReservationModal`, `reservationService` y `/app/reservations`, sin checkout ni pagos. Cada franja fechada reserva un espacio completo para un grupo y queda pendiente de aprobación. El delegado activa la prueba y publica horarios por espacio desde Mis lugares → Reservas y horarios. Aplicar primero `202610120004_trial_reservations.sql`; el piloto queda apagado por defecto. Orden y límites: `docs-local/supabase/TRIAL_RESERVATIONS.md`.
- El modal de reservas usa el calendario compartido con días publicados, fechas civiles sin conversión a UTC y horarios de Chile continental. Sus encabezado, cierre y pie permanecen fuera del contenido desplazable. La carga semanal usa `publish_reservation_week`, atómica e idempotente para una semana fechada por espacio; no recurre automáticamente. `set_reservation_day_enabled` modifica sólo franjas libres y futuras, conservando reservas y excepciones. Aplicar `202610120006_weekly_reservation_schedules.sql` antes de publicar este frontend; no reemplazar la operación semanal por siete solicitudes independientes.
- Reservas del delegado y Mis reservas escuchan un canal privado por cuenta mediante `reservationRealtimeService` y `useReservationFeed`. Aplicar `202610120005_reservation_realtime.sql` después de la seguridad de canales y del piloto. Los avisos sólo contienen `changed: true`; las lecturas siguen verificando RLS. Agrupar ráfagas, recargar al reconectar/volver a la pestaña, descartar respuestas antiguas y liberar el canal al desmontar. No agregar consultas periódicas para detectar cambios.
- El panel de delegado comparte `DelegatePage`, skeletons y `useDelegateData`. Lugares, reportes, suscripción, perfil y resumen reutilizan cachés privadas en memoria de cinco minutos, con deduplicación y limpieza al cambiar de cuenta. Las actualizaciones de reservas por Realtime invalidan las cachés relacionadas y fuerzan una lectura nueva. `get_delegate_reservations(200, offset)` devuelve reservas y nombres autorizados sin consultar primero el catálogo; requiere `202610120007_delegate_reservation_feed.sql` antes del frontend. Mantener su alcance en el servidor y la paginación sin perder registros. El listado de lugares usa `reservations(count)`, no descarga todos sus IDs para contarlos.

## Convenciones de implementación

- Leer primero los archivos de la funcionalidad y sus servicios. Realizar cambios centrados en la solicitud, respetar cambios locales existentes y evitar refactorizaciones ajenas al objetivo.
- Mantener las pantallas en su carpeta de `features`; compartir componentes sólo cuando exista reutilización. Centralizar nuevas consultas y operaciones de negocio en `services` y reutilizar el cliente Supabase existente.
- Seguir el estilo de los archivos editados: componentes funcionales, hooks y tipos explícitos. Evitar introducir `any` o desactivar comprobaciones para ocultar errores.
- El alias `@/` apunta a `src/`; también existen imports relativos. Mantener coherencia con el módulo que se modifica.
- La navegación web usa React Router y se define en `routes.tsx`. Conservar los flujos de estudiante/trabajador, administrador y delegado, y el acceso público a `/terminos` y `/privacidad`.
- `/` muestra la landing; `/iniciar-sesion` conserva login/registro y un destino interno validado en `authNavigation.ts`. El catálogo público usa `publicPlaceService` y la RPC paginada `get_public_place_cards`, con sólo ID, nombre, foto principal y dirección de lugares activos. La dirección viaja en esa misma carga, instantánea inicial y caché pública: `LandingAccessDialog` la lee directamente del lugar seleccionado, sin solicitudes ni estados de carga al abrir el modal. Las tarjetas siguen mostrando sólo nombre/foto; horarios, servicios, coordenadas y cuentas no forman parte de la proyección pública. El modal comparte la vista del lugar y el acceso desde «Conocer lugares» en portada; el login/registro conserva el destino de la ficha o `/app/discover` y el carrusel se pausa mientras está abierto. Aplicar `202610210001`, `202610210002` y después `202610210003_public_place_card_addresses.sql` antes del frontend/build SEO. La última recrea la firma de la RPC en una transacción sin CASCADE y conserva las tablas privadas cerradas. La RPC anterior `get_public_place_preview(uuid)` se conserva para clientes antiguos; el frontend actual no la llama ni usa un servicio de vista previa separado. No reutilizar las fichas completas, métricas identificables ni geolocalización en la landing. Las rutas privadas también exigen entrar al flujo demo cuando Supabase está desactivado; `demoSessionService` nunca acredita una sesión de producción.
- SEO: el dominio canónico es `https://www.pinwi.cl`. `siteSeo.ts` centraliza páginas públicas, títulos, robots y datos estructurados. `seoPlugin` genera la landing y los documentos legales con sus mismos componentes React durante `npm run build`; los efectos no se ejecutan, no consulta Auth ni cuentas y no incluye el renderer de servidor en el cliente. Antes de renderizar, el build carga todas las páginas de la RPC pública mínima con la clave publishable/anon y las incorpora al HTML y a una instantánea JSON escapada. Si el backend configurado falla, el build falla en lugar de publicar un catálogo incompleto. Sólo la landing es indexable actualmente; los documentos legales mantienen `noindex, follow` hasta su revisión formal. Sitemap y robots se generan en `dist/` y se sirven también en desarrollo, sin fechas ficticias. `vercel.json` conserva las cabeceras de seguridad, sirve HTML público con `cleanUrls` y limita los rewrites al shell privado con `noindex`; no recuperar el rewrite global que convertía sitemap, robots y errores en la landing. La navegación SPA actualiza el head y retira canonical/JSON-LD de rutas privadas. Al agregar una página pública, revisar registro, renderer, indexabilidad y sitemap; no introducir fichas autenticadas ni tokens en metadatos. Iconos y logo públicos reutilizan el arte de Pinwi. Orden de validación y pasos de Search Console: `docs-local/seo/IMPLEMENTACION.md`.
- Redes y WhatsApp del footer se consultan con `siteSettingsService` y se editan en Administración → Gestión → Sitio público. La tabla `site_settings` tiene lectura pública y escritura sólo para administradores activos mediante RLS. Campos vacíos no generan enlaces. Su migración incremental local debe aplicarse antes del frontend; consultar `docs-local/supabase/PUBLIC_LANDING.md` para el orden de activación.
- La landing no carga Google Maps ni pide ubicación. Conserva todos los lugares activos en el HTML, sin buscador público. El carrusel reutiliza `components/ui/carousel`: muestra 12 tarjetas por página en escritorio (4 × 3), 9 en tablet y 6 en móvil, con tres filas y flechas centradas en los costados, sin contadores ni pie de paginación. Avanza automáticamente cada seis segundos en bucle; permite pausa manual y se detiene con hover, foco, arrastre, modal abierto, sección fuera de vista o pestaña oculta. El movimiento reducido desactiva el avance automático. Limpiar timers, observadores y listeners al desmontar. Las páginas fuera de vista salen de la navegación por teclado. Sin JavaScript conserva desplazamiento horizontal nativo. `publicPlaceService` pagina por ID, deduplica lecturas y conserva una caché pública en memoria de cinco minutos, invalidada al editar lugares. Las fotos usan imágenes nativas con `src`, dimensiones y carga diferida; no precargar todo el catálogo con efectos. Los cambios llegan al navegador al renovar la caché; actualizar el HTML indexable requiere volver a compilar y publicar.
- Gestionar carga, error, vacío y éxito en operaciones asíncronas. Mostrar éxito sólo después de la confirmación del servidor; limpiar suscripciones Realtime, observadores de ubicación y efectos al desmontar.
- La política de contraseñas nuevas se comparte desde `supabase/functions/_shared/passwordPolicy.ts`: entre 8 y 128 caracteres, con frases largas y sin el antiguo puntaje como requisito. No aplicar esta política al login de contraseñas existentes. Auth debe tener el mismo mínimo configurado en el servidor; `supabase/config.toml` sólo configura el entorno local.
- Recuperación: OTP numérico verificado por Auth y antigüedad máxima de diez minutos comprobada por la función Edge con `recovery_sent_at` del servidor. Los contadores atómicos sólo se consumen desde el servidor; el cooldown de correos en memoria es una ayuda de interfaz. No sustituir límites del servidor por `localStorage`, timers o headers de IP modificables por el cliente.
- Presencia y escritura usan canales privados; la autorización de participantes está en `realtime.messages`. Los reportes comunitarios usan `get_place_report_summaries`, sin autores ni notas de moderación. Aplicar `202610120001_auth_security.sql` y `202610120002_app_security.sql` antes de funciones/frontend y `202610120003_disable_account_oracle.sql` después del nuevo frontend. Orden y configuración: `docs-local/security/2026-10-12_APP_SECURITY.md`.
- Al modificar sesión, roles o datos almacenados, revisar `CurrentUserContext`, `currentUserService` y `appCacheService`. Evitar que una respuesta pendiente o caché de una cuenta termine mostrando datos en otra sesión.
- Al volver a una vista de administración, mostrar primero su caché en memoria y reutilizar las consultas recientes durante cinco minutos. Actualizar datos vencidos en segundo plano sin ocultar el contenido; reservar `forceRefresh` para una actualización explícita. Invalidar cachés relacionadas al guardar cambios y limpiar datos privados al cambiar de cuenta o cerrar sesión. No usar la caché como comprobación de permisos ni persistir estos datos privados en `localStorage`.
- Administración → Lugares usa `listManagedPlaces` y una caché propia para separar habilitados (`active`) y deshabilitados (`inactive`). El catálogo de usuarios y las tarjetas públicas siguen consultando sólo lugares activos. Deshabilitar conserva fichas, reservas e historial; habilitar requiere confirmar el estado devuelto por el servidor. No reutilizar el listado administrativo en pantallas públicas ni tratar estados `pending` o `deleted` como deshabilitados recuperables.
- La eliminación definitiva aparece sólo al editar como administrador, junto a Guardar en escritorio y debajo en móvil, con confirmación explícita. Usa `delete_managed_place`, comprueba administrador activo/verificado y elimina los registros vinculados por las claves foráneas; una política restrictiva impide DELETE de delegados incluso ante políticas heredadas. Aplicar primero `202610110001_admin_place_deletion.sql`. Después del borrado confirmado, limpiar las imágenes de su carpeta mediante Storage; un fallo de limpieza se informa como pendiente, sin repetir el borrado. Los delegados pueden editar y deshabilitar lugares asignados, sin eliminación definitiva.
- Las fichas de lugar tienen caché y deduplicación propias durante cinco minutos; una ficha individual no sustituye el catálogo completo. Regiones, ciudades e instituciones reutilizan la caché en memoria por filtro, invalidada al cambiar de cuenta. Las lecturas simultáneas del perfil comparten una solicitud por cuenta; guardar perfil, visibilidad o foto invalida también las respuestas pendientes, y `forceRefresh` conserva una lectura nueva cuando no hay otra en curso.
- No editar `dist/` ni `node_modules/` como código fuente. Conservar los plugins React/Tailwind, el resolver de recursos Figma y las restricciones de archivos privados de `vite.config.ts`.

## Interfaz y marca

- La landing incorpora una guía visual de pingüino con silueta de pin en `LandingGuide.tsx`, con el PNG transparente versionado `assets/pinwi-guide-v1.png`; es un personaje complementario, no reemplaza `BrandLogo`. La viñeta blanca queda a la izquierda y el personaje a la derecha; `.landing-guide-float` anima ambos como un solo grupo. `LandingJourney.tsx` agrupa los pasos y la presentación con `assets/pinwi-reading-v1.png`; el cierre usa `assets/pinwi-working-v1.png`. `useLandingMotion` y `landing-motion.css` limitan entradas y movimientos a la landing; la portada con dos fotos entra desde arriba y `data-landing-from` permite entradas desde izquierda, derecha o abajo en las secciones siguientes. Los revelados, incluida la portada, se repiten al regresar: un observador reactiva la entrada y otro la prepara sólo al salir completamente de un margen de 80 px para evitar parpadeos; `data-landing-return` invierte la dirección al volver desde abajo. El HTML inicial permanece visible sin JavaScript. Respetar movimiento reducido y pausar movimientos ambientales fuera de pantalla o con la pestaña oculta. Conservar los prompts de los personajes en `docs-local/brand/` para futuras variantes.
- Mantener los textos de la interfaz y las explicaciones al usuario en español, con tildes y archivos UTF-8. Conservar los identificadores técnicos según las convenciones existentes.
- Reutilizar `components/ui`, `cn` y los estilos/tokens existentes antes de agregar dependencias o crear componentes equivalentes. Tailwind es versión 4: no aplicar configuraciones de Tailwind 3 sin comprobar compatibilidad.
- Respetar la identidad de Pinwi y usar `BrandLogo`. El original es `assets/Logo_Pinwi.svg`; si cambia, revisar también `pinwi-mark.svg` y `pinwi-wordmark.svg`.
- Verificar diseños en móvil y escritorio, sin desbordamientos, con etiquetas de formulario, foco visible, navegación por teclado y respeto a movimiento reducido.
- Para precios en pesos chilenos, seguir el formato `es-CL` y `CLP` usado en la aplicación.

## Supabase, permisos y datos privados

- Antes de modificar permisos o SQL, consultar, si están disponibles, `docs-local/supabase/DELEGATES.md`, `docs-local/supabase/schema/README.md`, `docs-local/PRIVACY_AUDIT.md` y `docs-local/supabase/REMOTE_REVIEW.md`. Son documentos locales que no se incluyen al clonar el repositorio; sus fechas no prueban el estado remoto actual. Si faltan, revisar la implementación y solicitar los SQL locales necesarios antes de cambiar la base de datos.
- La autorización debe validarse en RLS, RPC o funciones del servidor. Las rutas privadas y los controles visuales no bastan. No confiar en metadatos de registro o estado del navegador para otorgar roles privilegiados.
- Mantener privadas las cuentas de `public.users` y los perfiles de `public.user_profiles`. Para identidades de otras personas, reutilizar `sharedProfileService` y la RPC `get_shared_profiles`; no abrir tablas privadas para solucionar una pantalla. El directorio académico es voluntario y revocable.
- Un delegado necesita cuenta y registro de delegado activos y sólo puede gestionar lugares de su alcance. Mantener las operaciones de roles/asignaciones atómicas y los cambios de estado de reservas restringidos en el servidor.
- Los espacios conservan sus UUID al editarse mediante `replace_place_spaces`; no borrarlos y recrearlos. Las reservas guardan nombre/horarios históricos y no permiten eliminar espacios con reservas futuras ni reducir su capacidad por debajo del grupo reservado. La creación es idempotente por usuario/solicitud, con exclusividad en PostgreSQL; no calcular autorización, precio o disponibilidad sólo en React.
- Al modificar mensajes o notificaciones, conservar el acceso por participantes/destinatario y la integridad del contenido. Las confirmaciones de lectura no deben permitir reescribir mensajes, incluidos los históricos.
- Todo valor `VITE_*` llega al navegador. Nunca colocar allí claves `service_role`, tokens administrativos, claves de Brevo ni contraseñas. No imprimir `.env`, enlaces con tokens ni datos personales en logs, respuestas o documentación.
- Conservar las exclusiones de `docs-local/`, `supabase/schema/`, `supabase/migrations/`, todos los archivos SQL, el estado de la CLI y los respaldos. No agregarlos a Git, ni con `git add -f`, ni incluirlos en despliegues. Los modelos, diagramas y documentación de la base de datos deben permanecer en `docs-local/`, aunque tengan otra extensión.
- `supabase/schema/pinwi_schema_supabase.sql` contiene borrados destructivos: usarlo sólo para bases vacías o descartables, como los fixtures locales de pruebas. No ejecutarlo sobre una base con datos existentes.
- Para cambios de esquema, crear una migración incremental nueva con versión posterior; no reescribir migraciones aplicadas. Si cambian permisos o funciones usadas por el frontend, documentar el orden de despliegue.
- Preparar y validar los cambios localmente. Aplicar migraciones remotas, publicar funciones/frontend o enviar invitaciones sólo dentro de una solicitud que autorice esas acciones; modificar código local no implica desplegarlo.
- Los documentos legales comparten contenido en `src/app/features/auth/legalDocuments.ts`, con versión, fecha e introducción independientes por documento. Los términos tienen redacción pública sin referencias a demostraciones; la política de privacidad conserva su estado de borrador. La revisión formal y la identificación legal del operador siguen pendientes antes de una versión definitiva. No inventar identidad legal, contactos, garantías de privacidad ni afirmar cumplimiento a partir de pruebas técnicas.

## Verificación y entrega

- No crear archivos Markdown de resumen por rutina: entregar el resumen en el chat. Cuando una tarea requiera un informe, guardarlo en `docs-local/`, conservando subcarpetas por tema. Mantener `README.md`, `AGENTS.md`, `CLAUDE.md`, las instrucciones de `guidelines/` y `ATTRIBUTIONS.md` en sus ubicaciones; son documentación esencial, instrucciones y atribuciones del repositorio.
- Para cambios de TypeScript/React, ejecutar `npm run typecheck` y `npm run build`. Si cambia lógica de servicios, sesión, permisos, mensajes o SQL, ejecutar también `npm test` y ampliar las pruebas de regresión cuando corresponda.
